# Как это устроено (кратко, по-русски)

## Общая схема

Три сервиса в `docker-compose.yml`: Postgres, backend на Go, frontend на React — отдаётся через nginx
после сборки. Backend — единственная точка входа в данные; всё, включая live-обновления, идёт через него.

## Путь метрики: от запроса до экрана

1. Клиент (демо-генератор на странице run или твой `curl`) шлёт `POST /runs/{id}/metrics` с телом
   `{batch_id, metrics: [...]}`. `batch_id` клиент генерирует сам и переиспользует при повторной отправке
   того же пакета.
2. Backend в одной транзакции: берёт advisory lock на этот run (чтобы вставки по одному run шли строго по
   очереди — подробнее ниже), пытается вставить строку в `batches`, при успехе вставляет все метрики в
   `metrics` и коммитит. После коммита рассылает каждую вставленную метрику в `internal/sse.Hub` — это
   просто карта `run_id -> подписчики` в памяти процесса.
3. Открытая страница run держит `fetch()`-стрим на `GET /runs/{id}/stream` (не `EventSource`, потому что
   `EventSource` не умеет слать свой `Authorization`-заголовок). Хендлер стрима сначала подписывается на
   Hub, потом читает из Postgres всё, что уже накоплено (`id > after_id`), потом досылает то, что Hub
   успел забуферизовать за время этого запроса, и только потом переключается на живую трансляцию.
4. На фронте каждая метрика просто кладётся в `Map<id, Metric>`; перед рендером весь набор пересортировывается
   по `(name, step, ts, id)` — порядок прихода по сети никак не влияет на порядок отображения.

## Как предотвращаются дубли

`batches` — таблица с первичным ключом `(run_id, batch_id)`. Повторная отправка того же `batch_id`
с тем же содержимым (по SHA-256 хэшу метрик) ловится на `ON CONFLICT DO NOTHING`: новых строк не
появляется, клиенту отвечаем `200 duplicate`. Если `batch_id` тот же, а содержимое другое — это уже не
ретрай, а ошибка клиента: `409`, ничего не пишем. Если два одинаковых запроса пришли одновременно —
один выигрывает вставку, второй ловит конфликт уникальности и доигрывает ту же логику сравнения хэша.
Проверено тестом с 10 параллельными одинаковыми запросами: ровно одна строка в базе.

## Как работает reconnect

Каждое SSE-событие несёт `id:` — это номер строки в Postgres (`metrics.id`), не имеющий отношения к
`step` или времени эксперимента. При разрыве клиент помнит последний полученный `id` и при новом
подключении шлёт его в заголовке `Last-Event-ID`. Backend сначала эту историю дочитывает из базы, а уже
потом переключается на живые события — поэтому ни одно событие, случившееся ровно во время переподключения,
не теряется и не дублируется (порядок: подписка → запрос в базу → слив буфера → живой поток).

Отдельно у клиента есть watchdog: если за ~8 секунд не пришло вообще ничего (даже heartbeat, который
сервер шлёт каждые 3 секунды), соединение считается подвисшим и переоткрывается — потому что тихий обрыв
сети сам по себе не всегда роняет TCP-соединение быстро.

## Как обеспечивается изоляция

У каждого проекта свой API-ключ; хранится только его SHA-256-хэш. Абсолютно каждый запрос к данным идёт
одним SQL-запросом вида `WHERE project_id = $свой AND id = $ресурс` — то есть чужой run и несуществующий
run для сервера неотличимы, оба дают одинаковый `404`. Это специально проверено тестом: угаданный случайный
ID и реальный ID чужого проекта возвращают побайтово одинаковый ответ. При ротации ключа старый
перестаёт работать мгновенно для новых запросов, а уже открытый стрим на старом ключе принудительно
закрывается в течение одного «тика» heartbeat (~3 секунды) — сервер на каждом тике перепроверяет, жив ли
ключ.

## Как запустить и проверить самому

```bash
docker compose up --build
```

Открой http://localhost:5173, подключись демо-ключом `sk_demo_project_a_local_only_0000`
(см. README.md), создай run, нажми «Start demo generator».

Тесты (стек должен быть поднят):

```bash
cd backend && go test ./... -v                                   # модульные тесты hub'а
cd tests/isolation && npm install && npm test                     # изоляция + silent failures
cd tests/e2e && npm install && npx playwright install chromium && npm test   # E2E + сверка с БД
cd tests/load && go run . -runs 50 -rate 10 -duration 30s         # нагрузка 50×10 событий/с
```

Сырой вывод всех прогонов сохранён в `docs/test-logs/`. Полная аргументация решений — в
`docs/design.md`, доказательства и вердикт SHIP/DON'T SHIP — в `docs/submission-note.md`.
